# Task

## Context
- 사진 게시물에 20장을 넘는 내용 이미지를 저장하고 원하는 페이지로 빠르게 이동할 수 있어야 한다.
- 배치판 드래그는 자유 좌표 이동이 아니라 페이지 사이 삽입으로 동작해야 한다.

## Current Understanding
- `photo_posts.image_paths` 배열 순서가 실제 페이지 순서의 SSOT다.
- `image_layout`은 페이지 순서를 다섯 열로 표현하는 파생 좌표로 유지한다.
- 모든 좌표는 배열 인덱스 기준 `x = index % 5`, `y = floor(index / 5)`로 생성하면 빈 슬롯을 원천 차단할 수 있다.

## Observed Issues
- 작성기, 편집기, Manager, 서버 정규화가 각각 20장 제한을 적용했다.
- 기존 드래그는 좌표만 교환하고 배열 순서를 바꾸지 않아 페이지 삽입 의미와 일치하지 않았다.
- 5×5 고정 CSS와 Y 좌표 상한 때문에 25번째 이후 행을 표현할 수 없었다.
- 기존 상하좌우 탐색은 저장 좌표에서 이웃 이미지를 찾아 페이지 인덱스 순서와 분리될 수 있었다.

## Decision Notes
- 다섯 열은 유지하되 행 수는 이미지 개수에 따라 계속 늘린다.
- 드롭 대상은 존재하는 페이지 인덱스로 제한하고, 배열 `splice` 후 모든 좌표를 연속 재생성한다.
- 상세 페이지 인덱스는 오른쪽 고정 격자 대신 하단 가로 스크롤 목록으로 제공한다.
- 현재 펼침면 인덱스를 다시 눌러 표지로 돌아가던 동작은 제거하고 해당 페이지 유지로 단순화한다.
- 각 페이지는 다음 인덱스로 이동할 빨간 방향 하나만 저장한다.
- 다음 페이지의 파란 복귀 방향은 직전 빨간 방향의 반대로 자동 계산하며 사용자가 별도로 저장하지 않는다.
- 빨간 다음 방향과 파란 복귀 방향이 같은 슬롯에 겹치면 다음 방향을 자동 보정한다.

## Initial Render Harness
- SSOT는 기존 `photo_posts.image_paths`의 배열 순서다.
- `NormalizePhotoPosts`가 서버와 브라우저에서 동일하게 전체 배열을 보존하고 연속 `ImageLayout`을 생성한다.
- 새 저장 필드나 mount 후 교체 경로는 추가하지 않는다.

## Implementation Notes
- UI와 Manager의 20장 상한 및 서버 정규화 `slice`를 제거했다.
- 작성기와 편집기의 추가·삭제·붙여넣기·드래그 결과를 항상 연속 페이지로 재번호화했다.
- Manager는 저장 입력의 좌표가 배열 순서와 정확히 일치할 때만 허용한다.
- 포토북 페이지 인덱스는 휠·터치 가로 스크롤과 직접 선택을 지원하며 활성 펼침면을 자동으로 중앙에 맞춘다.
- 작성기와 편집기 이미지 위에 네 방향 컨트롤을 배치하고 다음 방향은 빨강, 자동 복귀 방향은 파랑으로 표시한다.
- 상세 스크롤 보기에서는 빨간 방향이 다음 인덱스, 파란 방향이 이전 인덱스로만 이동한다.
- `image_layout.forward_direction`에 다음 방향을 저장하며 레거시 데이터는 충돌 없는 오른쪽 진행을 기본값으로 정규화한다.

## Result
- 32장 합성 게시물의 전체 이미지 보존과 빈칸 없는 좌표 `last=1:6`을 확인했다.
- 레퍼런스 방향 흐름과 복귀 방향 충돌 검사를 통과했다.
- TypeScript, 전체 ESLint, Next.js 프로덕션 빌드 통과.
